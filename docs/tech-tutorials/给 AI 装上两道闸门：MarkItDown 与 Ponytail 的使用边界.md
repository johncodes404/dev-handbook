# 给 AI 装上两道闸门：MarkItDown 与 Ponytail 的使用边界

AI 的效率常常不是输在模型不够聪明，而是输在两件事上：读进来的是混乱的文件，写出去的是多余的代码。

MarkItDown 处理前者，Ponytail 处理后者。它们不是“省 Token 神器”，而是两套把 AI 工作流拉回正轨的约束。

## 一、MarkItDown：把“给人看的文件”改造成“给模型读的材料”

- 官方项目：[microsoft/markitdown](https://github.com/microsoft/markitdown)
- Skill：[MarkItDown SKILL.md](https://github.com/K-Dense-AI/scientific-agent-skills/blob/main/skills/markitdown/SKILL.md)

### 它做什么

MarkItDown 是微软开源的文件转换工具，可将 PDF、Word、PPT、Excel、网页等转换为 Markdown。它会尽可能保留标题、列表、表格与链接等结构；它的目标是让模型检索、总结和分析，而不是像 Word 一样一像素不差地还原排版。

Markdown 的价值不在“格式更漂亮”，而在于它剥掉了页眉页脚、坐标、字体、断行等阅读噪声，把材料重新组织成模型熟悉的结构化文本。

### Skill 的设计思想

这个 Skill 不是一句“把 PDF 转成 Markdown”，而是一份操作规程：

1. **按输入分流**：本地文件、文件流、远程链接、扫描 PDF、OCR 分别走不同路径。
2. **优先最窄权限**：本地 PDF 用本地转换；不要把不可信 URL 直接交给万能接口。
3. **默认不外传**：OCR、云端识别、音频转写、插件可能把内容发往外部服务，私密材料需要先确认。
4. **批量化阅读**：支持整目录转换、文献库转换、保留来源信息与生成索引。
5. **保留原件校验**：双栏论文、表格、图片、脚注和扫描页容易出错；PDF 才是可引用的权威版本。

### 我应该怎么用

适合的工作流是：

> 下载论文/政策文件 → 转为 Markdown → 让 AI 按章节提炼论点、证据与问题 → 回到原 PDF 核对页码、引文和图表。

这特别适合文献综述、原著解读、政策材料整理。不要把“转换成功”理解成“可以直接引用”；它帮你加速阅读，不能替代核对。

扫描版 PDF 往往没有真正的文字层，此时基础转换效果会很差，需要额外 OCR。对只需要读正文的普通 PDF，先用基础本地转换即可，不必一开始就接云端 OCR。

## 二、Ponytail：阻止 AI 把一个小需求写成一个小公司

- 仓库：[DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)
- 核心规则：[Ponytail SKILL.md](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

### 它做什么

Ponytail 给 AI 设定“懒惰但不敷衍的资深开发者”人格。它不是自动扫描器，也不会神奇地发现所有可复用代码；它的作用是**强制 AI 在动手前先查、先复用、再决定是否需要写代码**。

它的核心决策阶梯是：

1. 这个功能真的需要存在吗？
2. 代码库里已有组件、工具函数或模式吗？
3. 标准库能解决吗？
4. 原生平台能力能解决吗？
5. 已安装依赖能解决吗？
6. 能否一行解决？
7. 最后才写最少的有效代码。

例如日期选择，原生 `<input type="date">` 可用时，就不必新装日期选择器、写包装组件、加一套样式和状态管理。

### Skill 的设计思想

它的设计并不只是“少写”，而是把“少写”限制在正确的地方：

- **YAGNI（你暂时不需要它）**：拒绝为未来假想需求预建接口、工厂、配置和脚手架。
- **复用优先**：先在仓库检索已有实现，避免同一个功能散落三份。
- **根因优先**：修 Bug 前查调用链，在共享入口修一次，而不是在多个页面反复打补丁。
- **删优于加**：能删的代码优先删，能用 CSS 的不用 JS。
- **安全不极简**：权限、输入校验、数据防丢、无障碍、必要测试不能被删掉。
- **保留升级出口**：如果为了简单选择了临时方案，要用 `ponytail:` 注释标出性能或规模上限与升级方向。

它有 `lite / full / ultra` 三档。默认 `full` 是“严格走决策阶梯”；`ultra` 则会更激进地挑战需求本身。

### 我应该怎么用

最适合在这些任务中开启：

- 微信小程序的单页样式、列表、搜索、状态切换；
- HTML/CSS 视觉原型；
- 已有项目里的局部修复与小功能；
- 你怀疑 AI 正在过度组件化、乱加依赖时。

推荐提示词：

```text
使用 Ponytail full：
先搜索并复用现有组件、样式和工具函数；
只修改这个页面，不新增依赖，不创建未被要求的抽象；
保留必要的边界校验。
完成后告诉我：复用了什么，以及刻意没有做什么。
```

涉及登录、权限、支付、数据删除、云函数和多人协作规则时，不要使用 `ultra`。此时目标不是“代码最少”，而是“风险最小且可维护”。

## 三、不要迷信“节省 50% Token”

这类宣传常把“某些极端案例”说成稳定收益。

MarkItDown 的收益主要是：减少文档噪声、提高检索和总结质量；它不必然等于你的模型账单减少一半。

Ponytail 的独立测试显示，在 80 组任务中，成本中位数约下降 10.3%，代码量中位数约减少 15.4%；只有原本很容易过度工程化的任务，收益才可能明显更高。另一个容易忽略的事实是：仅把 Ponytail 的 `SKILL.md` 放入目录，模型未必会自动启用；要获得稳定效果，需要明确点名使用，或采用其带 SessionStart hook 的插件安装方式。参见 [JetBrains 的独立测试](https://blog.jetbrains.com/ai/2026/07/ponytail-skill-claude-tested/)。

## 四、最终选择

**MarkItDown 值得长期配置。** 它是资料预处理流水线，尤其适合论文、政策文件与文档库。

**Ponytail 值得按任务开启。** 它是防止 AI 把简单需求过度工程化的刹车，尤其适合前端原型与局部功能修改。

一句话：MarkItDown 让 AI 少读垃圾，Ponytail 让 AI 少写垃圾；前者解决输入质量，后者解决输出膨胀。
